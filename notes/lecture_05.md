### A. 硬件基础与执行模型(p6–p15)

- [x] **Q1(p6)｜Dennard scaling 是什么?clock speed 是什么?与晶体管数量/尺寸什么关系?**
  > 原问(还原):Dennard scaling 具体讲的是什么?clock speed 是什么?这个和 transistors 的数量、大小有关系吗?
  - **一句话**:Dennard scaling 是"把晶体管做小,电压也同比例做低,于是**单位面积功耗不变**"这条经验规律 —— 它让 1980s–2000s 的芯片能靠"提频率 + 塞更多晶体管"免费变快,直到 2000s 中期失效。
  - **clock speed(时钟频率)**:芯片每秒的时钟周期数(GHz);它由"门延迟"决定(见下面第 3 步),是单线程速度的直接来源。
  - **严谨表述(分步推导)**:先约定记号,再一步步算 $C$、$V$、$f$,最后乘起来。
    - **第 0 步:动态功耗的公式从哪来**。CMOS 电路的主要功耗是"给电容充放电":单次翻转消耗能量 $\tfrac12 C V^2$($C$ 是负载电容,$V$ 是电源电压);每秒翻转 $f$ 次 ⇒ $P=\tfrac12 C V^2 f$,即 $P\propto C V^2 f$ ✓。所以"功耗怎么变" = "$C$ 怎么变 × $V^2$ 怎么变 × $f$ 怎么变" ✓
    - **记号**:设工艺进步一代,所有**线性尺寸**(栅长 $L$、栅宽 $W$、氧化层厚 $t_{ox}$、连线宽)都缩小 $k$ 倍($k>1$;例如 $k=1.4$ 就是"尺寸变成上一代的 0.7 倍")✓。面积因此缩 $k^2$ 倍,同面积能放的管子数就是 $k^2$ 倍 ✓
    - **第 1 步:电容 $C$ 怎么变**。MOS 栅电容 $C=\varepsilon\,W L/t_{ox}$:分子是**面积** $WL$,缩 $k^2$ 倍;分母 $t_{ox}$ 是**长度**,缩 $k$ 倍 ⇒ $C\propto k^2/k=1/k$ ⇒ **$C$ 缩 $k$ 倍** ✓ 直觉:器件越小,栅上能装的电荷越少 ✓
    - **第 2 步:电压 $V$ 怎么变(这是 Dennard 的关键假设)**。电场 $E=V/d$($d$ 是特征尺寸)。要保证器件不被击穿/退化,必须**保持电场恒定**;而 $d$ 缩 $k$ 倍 ⇒ 要求 $V$ 也缩 $k$ 倍 ⇒ **$V\propto 1/k$** ✓ 这就是 "constant-field scaling" 这个名字的来历 ✓
    - **第 3 步:频率 $f$ 怎么变**。门延迟 $\tau=CV/I$($C$ 要充放电、$I$ 是驱动电流,$I$ 正比于器件宽度 ⇒ $I\propto 1/k$)✓。代入:$\tau\propto (1/k)\cdot(1/k)/(1/k)=1/k$ ⇒ 延迟缩 $k$ 倍 ⇒ 频率 $f=1/\tau\propto k$ ✓ 直觉:电荷少了、电压低了,但驱动电流也同比例小了,净效果是"开关更快" ✓
    - **第 4 步:单管功耗**。代回 $P\propto C V^2 f=(1/k)\cdot(1/k)^2\cdot k=1/k^2$ ⇒ **单管功耗缩 $k^2$ 倍** ✓
    - **注意一个常见混淆**:单次翻转的**能量** $\tfrac12CV^2\propto 1/k^3$(因为它不含 $f$);而**功率** = 能量 × 每秒翻转次数,次数涨了 $k$ 倍,所以是 $1/k^3\cdot k=1/k^2$ ✓ —— 看到"缩 $k^3$"的说法时,它讲的是能量,不是功率 ✓(本笔记上一版就把两者写混了,已改正)
    - **第 5 步:功率密度**。功率密度就是单位面积的功耗。单位面积管子数 $\propto k^2$,单管功耗 $\propto 1/k^2$ ⇒ 功率密度 $\propto k^2\cdot 1/k^2=1$,**不变** ✓ —— 此时单位面积功耗不变，则总面积一定的情况下，总功耗不变。这就是 Dennard scaling 的全部结论:每代芯片"更密（晶体管数量更多） + 更快（每个晶体管频率更高）",而"每平方毫米发热"不涨 ✓
    - **数值例子**($k=1.4$,即尺寸 0.7 倍的一代):$V:1\to0.71$、$C:1\to0.71$、$f:1\to1.4$ ⇒ 单管功耗 $0.71\times0.71^2\times1.4\approx0.51$(约减半);管子密度 $1.4^2\approx1.96$ 倍 ⇒ 功率密度 $0.51\times1.96\approx1.0$ ✓
  - **所以"和晶体管数量/尺寸的关系"**:尺寸缩 $k$ 倍 ⇒ ① 同面积能放的管子数增 $k^2$ 倍;② 单管功耗降 $k^2$ 倍;③ 延迟降 $k$ 倍(频率可升 $k$ 倍)⇒ **等功耗下密度 ×$k^2$、速度 ×$k$** ⇒ 这就是"免费午餐" ✓
  - **为什么 2000s 中期失效**:第 2 步的前提崩了 —— 阈值电压不能无限降(室温下亚阈值摆幅下限约 $60\,\mathrm{mV/decade}$,再降就漏电爆炸)⇒ 供电电压停在 ~1V 附近降不下去 ⇒ 电场随尺寸继续上升 ⇒ 单管功耗不再按 $1/k^2$ 降 ⇒ **功率密度上升** ⇒ 频率停在 ~3–4 GHz,多出来的晶体管"开不起"(dark silicon)⇒ 转向多核与专用加速器 ✓
  - 讲义落点(P6):"传统的 scaling(Dennard)已经 tapped out"⇒ 于是要靠 **GPU 的并行 scaling**(P7:10 年 >1000×)✓
  - 参考:Dennard et al. 1974(IBM J. Res. Dev.);[Wikipedia: Dennard scaling](https://en.wikipedia.org/wiki/Dennard_scaling)(指数表:$C^{-1}$、$I^{-1}$、$\tau^{-1}$、$P^{-2}$、功率密度 $0$);"power wall / dark silicon" 见 Hennessy & Patterson《计算机体系结构》。

- [x] **Q2(p8)｜"CPU 为快速串行执行设计"如何理解?complex control flows、control unit、ALU 分别是什么?**
  > 原问(还原):cpu is designed for quick serial execution,如何理解?和 gpu 的设计不同点?cpu 有着 complex control flows,又如何理解?control units 和 ALU 分别是啥?
  - **一句话**:CPU 把大量芯片面积花在"让**一条指令流**尽快跑完"的硬件上(分支预测、乱序执行、大缓存);GPU 把面积花在"海量 ALU"上,靠多线程并行提高**总吞吐**。
  - **"quick serial execution"**:一个 CPU 核同一时刻只跑少数几个线程,但每个线程的**依赖链**被硬件加速推进(深流水线、乱序、推测执行、预取)⇒ 单线程延迟低 ✓
  - **"complex control flows"**:真实程序里大量 `if/else`、循环、函数调用、间接跳转 ⇒ CPU 需要**分支预测 + 推测执行 + 流水线冲刷恢复**等复杂控制逻辑来处理这些不规则的控制流 ✓;GPU 的控制逻辑简单得多(见 Q10 的 warp divergence 代价)✓
  - **control unit(CU,控制单元)**:负责**取指、译码、发射、调度、处理分支**的部件(它指挥数据通路"做什么")✓;**ALU(算术逻辑单元)**:真正做**加减乘除与逻辑运算**的部件(它"动手算")✓
  - **两者的面积分配**(P8 那张经典对比图):CPU 里 CU + 大 cache 占比高、ALU 少;GPU 里 ALU 密密麻麻、CU/cache 占比低 ⇒ 这正是"CPU 优化延迟、GPU 优化吞吐"的物理体现 ✓
  - 参考:讲义 P8 引的 [NVIDIA CUDA refresher](https://developer.nvidia.com/blog/cuda-refresher-reviewing-the-origins-of-gpu-computing/)。

- [x] **Q3(p8)｜"两者 optimize for 不同东西"具体指什么?throughput 是什么?**
  > 原问(还原):这里说的 CPU 和 GPU 两者 optimize for 的不同东西,具体是什么含义?throughput 是啥?
  - **一句话**:CPU 优化 **latency(单个任务多快完成)**,GPU 优化 **throughput(单位时间完成多少任务)**。
  - **latency(延迟)**:一个任务从开始到结束的时间(例如"一个 token 的前向要 10 ms")✓
  - **throughput(吞吐)**:单位时间完成的工作量(例如"每秒处理多少个 token / 多少次浮点运算")✓ —— 在 GPU 计算语境里常具体化为 **FLOP/s**(见 Q9)✓
  - **两种优化是冲突的**:要降低单线程延迟,就得堆复杂控制(乱序/预测/大 cache),费面积且难并行;要提高吞吐,就用大量简单核 + 超多线程,靠**线程切换掩盖延迟**(每个线程本身更慢)✓
  - **直觉**:CPU 像"几个熟练工",GPU 像"几千个新手"——单件活 CPU 快,但批量活 GPU 总产出高 ✓。所以矩阵乘(大量独立乘加)适合 GPU,而串行逻辑/分支密集的代码适合 CPU ✓

- [x] **Q4(p9)｜shared memory 与 L1 缓存的作用区别?shared memory 可以被编程吗?**
  > 原问(还原):shared memory 和 L1 缓存的作用区别?shared memory 能被 programming?
  - **一句话**:物理上它们是 SM 里**同一块 SRAM**,区别在**谁管理**:L1 由硬件自动缓存(你管不了),shared memory 由**程序员显式分配**(`__shared__`,你自己 load/store)✓
  - **L1 cache**:硬件自动决定"缓存什么、替换什么、命中与否";程序员只能通过**访问模式**间接影响它,无法保证某个数据一定在 L1 ✓
  - **shared memory**:block 内所有线程共享的一块**显式**存储;你在 kernel 里声明、自己写入、自己读取、自己同步(需要 `__syncthreads()`)✓ ⇒ **能被"编程"** ✓ 这就是 tiling 的前提(Q21)✓
  - **作用区别**:L1 是为了"**自动**捕捉时间/空间局部性";shared memory 是为了"**手动**把 tile 放进片上、反复复用"(把 $O(N)$ 次全局读变成 $O(N/T)$ 次,见 Q21/Q22)✓
  - 补充:shared memory 是 **block 级**的(跨 block 不共享,跨 block 只能走 global memory,见 P12)✓;L1 是 **SM 级**的缓存 ✓;NVIDIA 从 Kepler 起 L1/shared 共用同一块物理 SRAM,可按需划分大小 ✓

- [x] **Q5(p10)｜SRAM 和 DRAM 的全称是什么?**
  > 原问(还原):SRAM 和 DRAM 全称是什么?
  - **SRAM = Static Random-Access Memory**(静态随机存取存储器):每 bit 用 6 个晶体管(触发器)存,不需要刷新 ⇒ **快**;但面积大、贵 ✓ 用于 **L1 / shared memory / L2(片上)** ✓
  - **DRAM = Dynamic Random-Access Memory**(动态随机存取存储器):每 bit 用 1 个晶体管 + 1 个电容存,电荷会漏 ⇒ 需要**周期性刷新**;便宜、密度高 ⇒ **慢** ✓ 用于 **global memory(HBM 就是堆叠封装的 DRAM)** ✓
  - 讲义 P10 的量化:**SRAM 贵约 100 倍,但快约 8 倍** ✓ ⇒ 所以存储层次是"小容量快 + 大容量慢"的金字塔,优化的核心就是"让数据尽量待在离 SM 近的地方"(tiling/fusion 的动机)✓
  - 一张表帮你记:**寄存器 > shared/L1(SRAM)> L2(SRAM)> global(DRAM/HBM)> 磁盘**;越往下越大、越慢、越便宜 ✓

- [x] **Q6(p11)｜shared memory 与 L1 cache 的区别?为什么说 "we don't get control of L1 cache"?**
  > 原问(还原):shared memory 和 L1 cache 的区别是啥?为什么说 we don't get control of L1 cache?
  - **同 Q4**:两者是同一块物理 SRAM,区别在于**控制权**——L1 归硬件,L1 的内容/替换策略/是否命中你都**无法编程指定**;shared memory 归你,显式读写 ✓
  - **"we don't get control of L1 cache" 的确切含义**:做 tiling 时你不能说"请把这个 tile 锁在 L1 里";缓存可能因为别的数据流而被替换掉 ⇒ 你**无法保证**复用发生在片上 ✓
  - **所以要用 shared memory**:你手动把 tile 拷进 shared memory,它就一直待在那儿、直到你算完 ⇒ **复用是可保证的** ✓ 这正是 tiling 的关键一步(P41:"repeated reads now access shared, not global memory")✓
  - **一句对比**:L1 = "硬件帮你猜"(best-effort);shared = "你自己安排"(deterministic)✓

- [x] **Q7(p13)｜TPU 相比 GPU 的主要区别?**
  > 原问(还原):TPU 相比 GPU 的主要区别?
  - **相同点**(P13 原话):都是"**轻量控制 + 大而快的矩阵乘单元 + 快速内存**"的加速器 ✓
  - **主要区别**:
    ① **没有 warp**(P13:"no warps (just blocks)"):GPU 以 32 线程的 warp 为执行粒度、靠 SIMT 隐藏延迟;TPU 的抽象更粗,把整个矩阵运算交给**脉动阵列(systolic array)**,对 matmul 极高效,但**非 matmul(逐元素、控制流)不友好** ✓
    ② **数量/尺度**:GPU 有**很多 SM**;TPU 有**很少的 TC(张量核)**,但单个 TC 的 matmul 吞吐很大 ⇒ "数量少、单体强" ✓
    ③ **互联方式**不同(下一讲 parallelism 展开)✓
    ④ **编程模型**:CUDA vs XLA/JAX ✓
  - 参考:讲义 P14 引的 [JAX scaling book: GPUs](https://jax-ml.github.io/scaling-book/gpus/) ✓

- [x] **Q8(p15)｜SIMT model 是什么?为什么说它让编程变简单?**
  > 原问(还原):这里的 SIMT model 是啥?为啥让 program 变得简单了?
  - **SIMT = Single Instruction, Multiple Threads**:一条指令**同时作用于多个线程**(每个线程有自己的寄存器和数据);硬件把同一 warp 内 32 个线程的同一指令一起发射 ✓
  - **为什么"简单"**:你写的是**标量代码**——就以"一个线程"的视角写 `out[i] = relu(in[i])`,不需要手写向量化(SIMD intrinsics)、不用关心数据如何打包成向量 ✓ 硬件负责"把 32 个线程凑成一条指令"✓
  - **代价**:① 同一 warp 内线程走不同分支时会串行化(divergence,见 Q10);② 需要大量线程来掩盖延迟(线程数不足时吞吐掉)✓
  - 一句话:SIMT 让你写"每个线程一人份"的朴素代码,却能吃满"一群人同时干"的硬件 ✓
  - **追问(2026-10-19)｜为什么非要"32 个线程共用一条指令"?数据不同算并行吗?为什么不让每个线程独立取指?"instruction" 是一个浮点运算吗?**
    - **一句话**:SIMT 把"**控制**"和"**数据通路**"拆开 —— PC、取指、译码、调度由 32 条 lane **共享一份**,寄存器和 ALU 每条 lane 各有一套 ⇒ 用 1/32 的控制开销换 32 倍的 ALU 密度;代价是 warp 内必须同指令(Q10 的 divergence)✓
    - **先把三个词拆开**:① **程序** = 一条指令序列,PC 沿着它走;② **线程(lane)** = 一份私有寄存器 + 私有内存视角的执行上下文;③ **指令** = ISA 级的一次操作(见下面的表,不等于"一个浮点运算")✓。SIMT = **多条 lane 共享同一个 PC / 指令流**:同一时刻所有 lane 的 PC 相同、寄存器不同 ✓
    - **硬件怎么做的**:SM 分成 4 个 partition,每个 partition 一个 **warp scheduler**;每周期,scheduler 从"就绪的 warp"里挑一个,**取一条指令、译码一次**,再把 32 条 lane 各自的寄存器操作数读出来送给 ALU 阵列 ✓ —— 以 A100 为例,每个 partition 16 个 FP32 单元,所以一条 32-lane 的 FP32 指令要 **2 个周期**才算完,但**取指/译码只做了一次** ✓;每条 lane 有自己的寄存器切片(每线程最多 255 个 32-bit 寄存器)⇒ "同一条指令、不同操作数"是天然的 ✓;SM 里同时驻留几十个 warp 轮转发射,用来掩盖延迟(呼应 Q3)✓
    - **"数据不同"正是并行的来源**:同一段程序作用在 32 份数据上 = 数据并行;矩阵乘里最常见的映射就是"**一个线程算一个(或一小块)输出元素**",32 条 lane 同时算 32 个输出 ✓
      ```c
      // 线程 i 负责一个输出元素：同一句指令，32 个 lane 的 i 不同
      __global__ void add(const float* a, const float* b, float* c, int n) {
          int i = blockIdx.x * blockDim.x + threadIdx.x;
          if (i < n) c[i] = a[i] + b[i];
      }
      ```
      **指令计数**:这一句大约编译成 5 条指令(算下标、两次 load、一次 add、一次 store);一个 warp **只发射这 5 条**,每条覆盖 32 个元素;若"每线程独立取指",同样的工作要 $32\times5=160$ 次取指/译码 ⇒ **控制开销差 32 倍** ✓
      **矩阵乘**:$32\times32$ 输出、一线程一元素 ⇒ 1024 线程 = 32 个 warp,每线程做 $K$ 次 FFMA ⇒ warp 指令数 $32K$;每条 FFMA 算 32 个 lane 的乘加 $=64$ FLOPs ⇒ 总 FLOPs $32K\times64=2048K$,与"每线程 $2K$ FLOPs × 1024 线程"完全一致 ✓
    - **instruction 是一条浮点运算吗?不是** ✗:

      | 指令 | 例子 | 每条指令(每 lane)的运算量 |
      | --- | --- | --- |
      | 浮点加/乘 | `FADD`、`FMUL` | 1 FLOP |
      | 乘加融合 | `FFMA`(a*b+c) | 2 FLOPs |
      | 访存 | `LDG`、`STG` | 0 FLOP(但可能要几百周期) |
      | 整数/地址 | `IADD`、`IMAD` | 0 FLOP(算下标/地址) |
      | 特殊函数 | `MUFU.EX2`(exp2) | 一次超越函数近似 |
      | 张量核 | `HMMA` | 每条 warp 指令几百~几千 FLOPs |

      ⇒ 一条 **warp 指令** = 32 条 lane × 这条指令 ⇒ 算 FLOPs 要用"指令数 × lane 数 × 每指令 FLOPs" ✓(Q9 里 MFU 的分子就是这么来的 ✓)
    - **为什么不做成"每个线程独立取指"**(= MIMD / CPU 路线):① **成本**:每条 lane 都要 PC + 取指 + 译码 + 记分牌 + 调度 ⇒ 控制硬件按 lane 数翻倍,芯片面积里 ALU 的占比掉下来(对照 P8 的 CPU/GPU 对比图:CPU 把面积给了控制与 cache,GPU 给了 ALU)⇒ 单位面积/单位功耗的算力大幅下降 ✓;② **收益小**:GPU 的目标负载(图形、矩阵、逐元素)本身就是"同一程序、不同数据",为用不上的灵活性付费不值 ✓;③ **其实 warp 之间本来就是独立的**:SM 里几十个 warp 各有自己的 PC 和指令流,4 个 scheduler 每周期各挑一个发射 ⇒ "独立指令流"是有的,只是**粒度是 32 条 lane**;想细化到 1 条 lane,成本与收益不成比例 ✓
    - **为什么恰好是 32**:太小 ⇒ 控制开销摊不薄;太大 ⇒ ① divergence 代价大(最坏 32 条路径,Q10)② 寄存器文件/调度粒度粗、尾部利用率差;另外 32 lane × 4B = **128B**,正好一条 cache line / 一个 burst(Q18)⇒ coalescing 天然对齐 ✓。业界:NVIDIA 用 32,AMD 用 64(wavefront)✓
    - **这个设计的代价**:warp 内 divergence(Q10)、不规则负载(指针追逐、稀疏访存)效率低、lane 利用率受问题并行度限制 ⇒ "GPU 适合矩阵乘、不适合分支密集的标量代码" ✓
    - **一个细节**:Volta 之后硬件给每条 lane 独立的 PC(independent thread scheduling),可让发散的不同子集交错推进;但每个 scheduler **每周期仍只发一条指令** ⇒ 灵活性↑、吞吐不变 ✓
    - 参考:[CUDA C Programming Guide: SIMT Architecture](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#simt-architecture)、Volta 白皮书(independent thread scheduling)、P8 引的 [CUDA refresher](https://developer.nvidia.com/blog/cuda-refresher-reviewing-the-origins-of-gpu-computing/) ✓

### B. 性能模型:throughput、divergence、精度(p21–p26)

- [x] **Q9(p21)｜throughput 的实际定义是什么?就是 FLOP/s(即 MFU 的分子)吗?**
  > 原问(还原):throughput 实际的定义,是不是就是 flops/s,也就是 MFU 计算公式的分子,代表实际每秒的运算量?
  - **你的理解基本正确** ✓:在 GPU 计算语境里,throughput 常被具体化成"**实际达到的每秒浮点运算数**"(FLOP/s)✓
  - **严谨表述**:$\mathrm{MFU}=\dfrac{\text{实际达到的 FLOP/s}}{\text{硬件标称峰值 FLOP/s}}$ ⇒ 分子确实是"实测吞吐"✓;分母是 spec 里的峰值(比如 H100 bf16 约 $989$ TFLOP/s,不含稀疏)✓
  - **两个易错点**:① 分子一般按"**模型需要的 FLOPs ÷ 墙钟时间**"算(与实现无关的"有用功"),这样 MFU 能反映"硬件有多少算力被你的算法真正用上";② 如果把**重算**(recomputation/checkpointing)额外花的 FLOPs 也算进去,得到的是 HFU(hardware FLOPs utilization),通常略高于 MFU ✓
  - **记忆**:throughput = 你实际跑出多少 FLOP/s;MFU = 它占峰值的百分比 ✓

- [x] **Q10(p23)｜control divergence:为什么 AB 和 XY 两个分支都要算,不能只算一个?**
  > 原问(还原):详细解释下这个例子。我不理解为啥需要同时计算 AB 和 XY 两个分支,而不是根据具体代码条件,只需要计算一个分支即可?
  - **一句话**:一个 warp 的 32 条 lane **共享同一个程序计数器(PC)** —— 同一时刻只能执行**同一条指令**;若 32 条 lane 的条件取值不一致,硬件只能"发 A(把走 else 的掩掉)→ 发 X(把走 if 的掩掉)→ 发 B → 发 Y",把两条路径**串行**跑一遍 ⇒ 所以"两个分支都要算" ✓
  - **讲义原文(P23)**:
    ```c
    if (threadIdx.x < 4) {
        A;
        B;
    } else {
        X;
        Y;
    }
    Z;
    ```
    右边图的横轴是时间,每根竖条是一个 lane(上下两半分别代表"满足条件"和"不满足条件"的两组线程);灰色 `divergence` 那段里,上半组活跃时下半组是黑的(被 mask),反之亦然;出了 if 之后两组在 `Z;` 处 **重新汇合(reconverge)**,又恢复满 32 lane 并行 ✓
  - **逐拍推演(讲义例子,一个 32 线程的 warp)**:`threadIdx.x` 在 warp 内是 0..31 ⇒ lane 0–3 满足 `x < 4`(4 条),lane 4–31 走 else(28 条)。硬件实际发射 5 条语句:

  | 发射次序 | 语句 | 活跃 lane | 被 mask 的 lane |
  | --- | --- | --- | --- |
  | 1 | `A;` | 0–3(4 条) | 4–31(28 条) |
  | 2 | `X;` | 4–31(28 条) | 0–3(4 条) |
  | 3 | `B;` | 0–3(4 条) | 4–31(28 条) |
  | 4 | `Y;` | 4–31(28 条) | 0–3(4 条) |
  | 5 | `Z;` | 全部 32 条 | 无(已 reconverge) |

  - **数值账(每句按 1 拍算)**:① 理想情况(所有 lane 同路)只需 `A,B,Z` 或 `X,Y,Z` = **3 拍**,实际 **5 拍** ⇒ 慢 $5/3\approx1.67$ 倍 ✓;② 只看发散区段(第 1–4 拍):发射容量 $4\times32=128$ 个 lane-槽,有用工作 $4\times2+28\times2=64$ ⇒ **利用率恰 50%** ✓ —— 两个分支**等长**时,无论 4/28 还是 16/16,都是 50%:代价只取决于"有几种不同的路径、各多长",与"每边多少线程"无关 ✓;③ 端到端算上 `Z`:有用 $96$ / 发射 $160$ ⇒ **60%** ✓
  - **为什么不能"按条件只算一个"**:SIMT 的执行单元是"**一条指令 × 32 条 lane**"——每个周期从 warp 取**一条**指令广播给 32 条 lane,配套一个 32 位的活跃掩码;没有"每条 lane 各自有 PC、各跑各的"机制(那是 CPU 的多线程)⇒ **分支粒度只能对齐到 warp** ✓(Volta 之后硬件支持 independent thread scheduling,可让不同子集交错推进,但每周期仍只发一条指令 ⇒ 代价依旧存在,只是调度更灵活 ✓)
  - **两种情况,硬件处理方式不同**:① **分支很短**(几条指令)时,编译器改用**谓词化(predication)**——不跳转,两条都算,再用 `selp` 选结果 ⇒ 没有跳转/reconverge 开销,但两边的计算量照样都付了 ✓;② **分支较长**时,走"分支 + lane 掩码 + reconverge",就是讲义这张图 ✓
  - **代价的极端**:若 32 条 lane 的条件各不相同(比如按数据值比较后分支),最多要串行 **32 条路径** ⇒ 有效算力只剩 $1/32$ ✓;嵌套 $m$ 层 if ⇒ 最坏 $2^m$ 条路径 ✓
  - **为什么标 "not a memory issue"**:发散期间程序**并没有多搬字节**(全局读写量不变),被浪费的是**发射槽/ALU 周期**,即"有效算力"↓。放到 roofline 上看:横轴的"可达峰值"被乘上一个利用率因子 ⇒ 原本 compute-bound 的 kernel 可能因此显得像 memory-bound ✓
  - **怎么缓解**:① 让条件在 **warp 粒度上一致**(按条件排序/分桶后再算,使同一 warp 内条件相同)✓;② 用**算术代替分支**——`r = cond ? a*b : x*y`(谓词化)或乘 0/1 掩码;attention 的因果 mask 正是这么做的:不写 `if (j ...)`,而是给分数加 $-\infty$ ✓(这就是 L4 的 mask 与 L5 这一条的联系);③ 把分支挪到 **block 粒度**(`if (blockIdx.x ...)`),让整个 block 走同一条路 ✓
  - **追问(2026-10-19)｜divergence 只出现在 if/else 里吗?纯"算乘法"这种直线代码会不会也要 mask 一部分 lane?**
    - **结论**:对 —— **发散来自"控制流",不来自"计算"**。纯直线代码(load → multiply → add → store)只有一条指令序列,32 条 lane 每条都执行同样的指令、只是寄存器不同,所以**不会出现"一部分 lane 被 mask、要分几趟走"** ✓
    - **四个需要注意的点**:
      1. **mask 是硬件的常规机制,不是 divergence 的专利**。每条 warp 指令都带一个活跃掩码;divergence 特指"掩码随控制流**分裂**,不同子集要**分时**走不同指令" ✓ —— 直线代码里掩码始终是"全 1",所以没有这笔开销 ✓
      2. **"尾部"照样闲置 lane**:最后不足 32 个线程的 partial warp、以及 `if (i < n)` 这类边界检查,都会让一部分 lane 不干活 ⇒ 这部分浪费**与 if/else 无关**、天然存在 ✓(边界谓词化比真分支便宜,但"空 lane"的浪费还在)
      3. **发散不止 if/else**:`for/while` 的**次数按数据变化**(变长序列、稀疏 gather、指针追逐)、`switch`、提前 `return`、短路 `&&`/`||`、按值取 min/max、断言/NaN 检查……只要跳转条件依赖**本 lane 的数据**,都会发散 ✓;反之,条件只依赖 `blockIdx` 或标量参数(整 warp 同一答案)时**不会**发散 ✓
      4. **短分支会被谓词化**:`r = cond ? a*b : x*y` 编译成"两边都算 + `selp` 选结果"⇒ 没有"分趟走",但**两边的计算量都付了** ⇒ "没有 mask 分裂"不等于"没有浪费" ✓
    - **回到你的例子**(矩阵乘 / 逐元素乘法):稠密矩阵乘的内层循环次数是**统一的**(都是 $K$),所以不发散,32 条 lane 一起做 FFMA ✓ —— 此时瓶颈通常转到别处:访存是否 coalesced(Q18–Q20)、tiling 复用够不够(Q21)、对齐与波量化(Q23/Q24)、寄存器与 occupancy ✓。**"没有 divergence"只说明这一项不亏,不代表快** ✓
    - **一个真实世界的反例**:变长序列组成的 batch(varlen)里,各样本的循环次数不同 ⇒ 同一 warp 内的 lane 走不同次数 ⇒ 发散/空转 ⇒ 这正是 padding、varlen kernel、按长度分桶(bucket)存在的理由之一 ✓

- [x] **Q11(p24)｜低精度缓解 memory-bound、提速推理——这算不算"牺牲精度"的取舍?**
  > 原问(还原):这里要如何理解?low precision 能一定程度上缓解 memory-bound,所以能够增大推理速度?那么这个不是也是一种取舍吗?相当于放弃了计算的精度?
  - **是取舍,但通常"几乎免费"** ✓:低精度确实降低数值精度,但深度学习的冗余很大,bf16/fp16 往往对最终质量影响很小;真正需要小心的是**动态范围/累加误差**(见下)✓
  - **为什么能提速**:每个元素字节数减半 ⇒ 同样的数据只需搬一半的字节 ⇒ **算术强度(FLOP/byte)翻倍** ⇒ 更容易摆脱 memory-bound ✓(讲义 P25 的 ReLU 例子:fp32 是 8 bytes/FLOP,fp16 是 4 bytes/FLOP ✓)
  - **还有第二条收益**:tensor core 对 fp16/bf16/fp8 的峰值吞吐更高 ⇒ compute-bound 场景也更快 ✓
  - **代价与对策**:① fp16 动态范围小(容易溢出/下溢)⇒ 用 **bf16**(范围同 fp32)或 **loss scaling**;② 累加误差 ⇒ 用 **fp32 累加**;③ 归一化/softmax/优化器状态保持 fp32 ✓(这就是 Q12 的混合精度)
  - 一句话:**低精度用"可接受的数值误差"换"带宽与算力"**,是 L5 里最划算的取舍之一 ✓

- [x] **Q12(p26)｜混合精度里为什么有时 16bit、有时 32bit?**
  > 原问(还原):这个图中的混合精度计算具体为啥要这样做?为什么有时候是 16bit,有时候是 32bit?
  - **原则一句话**:**"算"用低精度(吞吐高),**"存/累加/归一化"用高精度(稳)** ✓
  - **具体分工**(混合精度训练的通行做法):
    - **矩阵乘 / 卷积** ⇒ fp16 或 bf16:它们占了绝大部分 FLOPs,而 tensor core 在低精度下吞吐成倍提高 ✓
    - **累加(accumulation)** ⇒ fp32:哪怕输入是 bf16,点积的累加也要在 fp32 里做,否则误差累积 ✓
    - **归一化(LayerNorm/RMSNorm)、softmax、损失** ⇒ fp32:这些算子对数值范围敏感(指数、除法)✓
    - **优化器状态与主权重副本(master weights)** ⇒ fp32:更新量很小,低精度会被舍掉 ✓
  - **为什么不能全用 16bit**:fp16 的指数位少(范围 ±65504)⇒ 梯度/激活容易溢出或下溢;bf16 范围够但尾数只有 7 位 ⇒ 累加与更新会丢精度 ✓
  - **为什么不能全用 32bit**:带宽与 tensor core 吞吐都吃亏(见 Q11)✓
  - 讲义 P26 的图来自 NVIDIA 的 mixed-precision tutorial:横轴是不同精度、纵轴是 tensor core 的吞吐;可以看到"低精度快很多",但实际训练必须按上面的分工混合使用 ✓

### C. 低精度前沿、融合、重算与访存(p27–p49)

- [x] **Q13(p27)｜为什么 MXFP8 里"转置变得不确定(nontrivial)"?**
  > 原问(还原):这里完全没看懂。为啥 transpose matrix 出现了问题?出现了什么问题?如何解决的?
  - **背景**:MXFP8 是 **microscaling** 量化:每 **32 个连续元素**共享一个 scale factor(E8M0),元素本身用 E4M3(尾数多、范围小)✓
  - **问题**:转置会改变"哪 32 个元素在一起"——原本沿**行**方向的一组 32 个元素,转置后变成沿**列**拼起来的元素 ⇒ **scale 的归属关系被破坏** ✗。你不能"只把数字换个位置"就完成转置 ✓
  - **解决**(P28 的提示):"not all weights in MXFP8, transposes also separately quantized" ⇒ 为转置后的阵列**单独再做一份量化**(维护两套 scale 布局);或者反量化→转置→重新量化(更贵)✓
  - 一句话:低精度 + 块缩放把"矩阵 = 一堆数"变成了"矩阵 = 数 + 分组 scale",于是**任何改变元素相邻关系的操作(转置、重排)都要连带处理 scale** ✓

- [x] **Q14(p33)｜torch.compile 能自动做这种 fusion 吗?它和 JAX 是同一个东西吗?**
  > 原问(还原):torch compiler 应该能自动完成这里的这种 fusion 对吗?torch compiler 就是 JAX?
  - **能,但只限"简单"融合**:讲义原话 "'Easy' fusions like this can be done automatically by compilers (torch.compile)" ⇒ 像 $\sin^2x+\cos^2x$ 这种**逐元素(pointwise)** 链条合成一个 kernel,torch.compile 可以自动做 ✓
  - **但要小心**:跨 kernel 的 tiling、matmul 与逐元素的融合(如 FlashAttention)、手写调度 ⇒ 编译器往往做不了或做不好,仍需人写 ✓
  - **torch.compile ≠ JAX** ✗:两者都是"编译加速",但 torch.compile 是在 **PyTorch eager 语义之上**加一层图捕获(Dynamo)+ 后端编译(Triton/Inductor)✓;JAX 是**函数式**框架 + `jit` + XLA 编译 ✓ —— 思路相近,不是同一个东西 ✓

- [x] **Q15(p36)｜recomputation 到底怎么用"更多计算"换"更少访存"?fwd/bwd 的 read/write 分别指什么?**
  > 原问(还原):详细解释下这个例子,最好直接写出具体的计算公式和具体数值的结果…同时解释下,这一页和上一页 ppt 中,fwd 和 bwd 的这几次 read 和 write,分别指的是什么。
  - **先把两边数清楚**(这里的 read/write 都指**访问 global memory / HBM 的字节级事务**,不是寄存器):
    - **旧方案(P35,存激活)**:fwd = **1 read**(读 $x$)+ **3 writes**(写 $s_1$、$s_2$、$out$);bwd = **3 reads**(读 $s_2$、$s_1$、$dout$)+ **1 write**(写 $dx$)⇒ **8 次** ✓
      (为什么只存 $s_1,s_2,out$?因为 sigmoid 的导数可以由输出算出:$\sigma'(z)=\sigma(z)\bigl(1-\sigma(z)\bigr)$ ⇒ 最后一个激活直接用 $out$ 就够 ✓)
    - **新方案(P36,丢弃重算)**:fwd = **1 read**($x$)+ **1 write**($out$);bwd = **2 reads**($x$、$dout$)+ **1 write**($dx$)⇒ **5 次** ✓ 中间三个 sigmoid 在反向时**用 $x$ 重新算一遍** ✓
  - **代价与收益**:多花 **3 次 sigmoid 的前向**(逐元素、每次几十 FLOPs),省下 **3 次 HBM 访问**(每个激活一个张量、动辄 MB 级)⇒ 在 memory-bound 下**非常划算** ⇒ 这就是"用计算换带宽" ✓;讲义写的 **5/8** 就是 $5/8=62.5\%$ 的访存 ✓
  - **更一般的说法**(min-cut 重算):存哪些激活/不存哪些变成一个图上的割问题 —— 存得少⇒重算多、访存少;存得多⇒相反,最优解由"带宽 vs 算力"决定 ✓(P35/P36 引的 min-cut 文章就是讲这个)✓
  - **追问(2026-10-20)｜fwd 为什么只有 1 read?写完 $s_1$ 之后算 $s_2$ 不是还得把 $s_1$ 读回来吗?**
    - **一句话**:这里数的是**对 HBM(global memory)的读写次数**,不是寄存器访问;**融合后**的前向里 $s_1,s_2$ 一直待在寄存器里,从 $x$ 一路算到 $out$ 都不经过 HBM ✓
    - **关键在"写 $s_1$ 的目的"**:写 $s_1$ **不是为了算 $s_2$** —— 算 $s_2$ 用的是刚算出来、还在寄存器里的那个值;写它的唯一目的是**给反向存档**(反向要用 $\sigma'(z)=s(1-s)$)✓。同理 $s_2$ 是存档、$out$ 是真正的输出 ⇒ 前向的 3 次写 = **2 次存档 + 1 次真输出** ✓
    - **三种写法的 fwd 访存账**:

      | 写法 | fwd 的访存次数 | 说明 |
      | --- | --- | --- |
      | 不融合(每个算子一个 kernel) | 读 $x$、写 $s_1$ → 读 $s_1$、写 $s_2$ → 读 $s_2$、写 $out$ = **6 次** | 你说的"算 $s_2$ 要读回 $s_1$"正是这一种 ✓ |
      | 融合 + 存激活(P35 旧方案) | 1 读($x$)+ 3 写($s_1,s_2,out$)= **4 次** | 讲义 P35 就是这张账 ✓ |
      | 融合 + 丢弃重算(P36 新方案) | 1 读 + 1 写 = **2 次** | 中间量只在寄存器 ✓ |

    - **反向同理**:新方案的反向只读 $x$ 与 $dout$(2 次),重算出来的 $s_1,s_2$ 留在寄存器里,最后写 $dx$(1 次)⇒ 3 次 ✓ —— 若"重算"也把中间量落盘,那这次重算就白做了 ✓
    - **一句提醒**:讲义数的是"**张量级的访存次数**"(每个张量读/写各算一次),不是字节数;真实 kernel 里一次"读 $x$"对应很多个内存事务(见 Q18),但"8 vs 5"这个比例正是要传达的教学点 ✓
  - **追问(2026-10-20)之二｜bwd 为什么要读 $s_1$、$s_2$、$out$?就是为了算 $out$ 对 $x$ 的梯度吗?**
    - **是的,就是为了算 $\partial out/\partial x$(再乘上后面传来的 $dout$)**;而且**必须**读这些激活 —— 根源是 **sigmoid 的导数由它自己的输出决定**:$\sigma'(z)=\sigma(z)\bigl(1-\sigma(z)\bigr)=y(1-y)$ ⇒ 反向每过一层 sigmoid,都要知道那一层的输出 $y$ ✓
    - **先把前向写清楚**(3 层 sigmoid 串联,$out$ 是第三层的输出):$y_1=\sigma(x)$、$y_2=\sigma(y_1)$、$y_3=\sigma(y_2)=out$ ✓(P35 把 $y_1$、$y_2$ 存成 $s_1$、$s_2$,$y_3$ 就是输出 $out$ ✓)
    - **逐层推反向**(记 $\bar v=\partial L/\partial v$,$\bar y_3=dout$):
      - 第 3 层:$z_3=y_2$ ⇒ $\bar z_3=\bar y_3\cdot\sigma'(z_3)=dout\cdot y_3(1-y_3)$ ← **要读 $out$** ✓
      - 第 2 层:$z_2=y_1$ ⇒ $\bar z_2=\bar z_3\cdot\sigma'(z_2)=\bar z_3\cdot y_2(1-y_2)$ ← **要读 $s_2$** ✓
      - 第 1 层:$z_1=x$ ⇒ $\bar z_1=\bar z_2\cdot\sigma'(z_1)=\bar z_2\cdot y_1(1-y_1)$ ← **要读 $s_1$** ✓
      - 最后 $\bar x=\bar z_1$(因为 $z_1=x$,这一步的 Jacobian 是 1)✓
      ⇒ 合起来:$\bar x=dout\cdot y_3(1-y_3)\cdot y_2(1-y_2)\cdot y_1(1-y_1)$ ✓ —— 三个"$y(1-y)$"因子,分别来自三个被存下来的激活 ✓
    - **"为什么梯度需要它们"的一句话**:链式法则是"局部导数连乘";而 sigmoid 的局部导数 $\sigma'(z)=y(1-y)$ 是 **$y$ 的函数**,不是 $z$ 的 ⇒ 想知道局部导数,就得记住这一步的输出 ✓(这正是 P35 的 fwd 要写 $s_1,s_2,out$ 的原因:存的就是"将来算局部导数要用的量")✓
    - **数值例子**($x=0.5$、$dout=1$):$y_1=0.622459$、$y_2=0.650778$、$y_3=0.657186$;$\sigma'(z_1)=0.235004$、$\sigma'(z_2)=0.227266$、$\sigma'(z_3)=0.225293$ ⇒ $\bar x=0.225293\times0.227266\times0.235004\approx0.012033$ ✓ —— 与数值微分 $(f(x+h)-f(x-h))/(2h)$ 的结果一致(相对误差约 $4\times10^{-9}$)✓
    - **和讲义标注对齐一下**:P35 的 bwd 标的是 **3 次读:$s_2$、$s_1$、$dout$**;而按上式,第 3 层还要用 $y_3=out$ —— 真实实现里 $out$ 也会被读一次(PyTorch 的 sigmoid backward 就是 `grad * output * (1 - output)`),即 **4 读 + 1 写**。讲义把这页的账简化成了 3 次(相当于把 $out$ 当作"已在手");把这一项补上后,旧方案是 $4+5=9$、新方案仍是 $2+3=5$,**方向不变、比例从 5/8 变为 5/9** ✓
    - **代换到重算方案**:fwd 什么激活都不存 ⇒ bwd 只读 $x$ 与 $dout$,在**寄存器**里把 $y_1,y_2,y_3$ 重新算出来,再走上面同样的三层链式法则 ⇒ 多花 3 次 sigmoid 的计算,省掉 3 个张量的读写 ✓ —— 这就是"用计算换带宽"在反向里的具体样子 ✓
    - **更一般的规律**:反向需要的是"**局部 Jacobian 依赖的量**"——sigmoid / softmax 依赖输出,ReLU 依赖输入的符号,矩阵乘依赖另一个操作数,LayerNorm 依赖输入与统计量 ⇒ checkpoint 策略本质上就是"这些量里哪些留、哪些重算"的取舍 ✓
  - **追问(2026-10-20)之三｜fwd 算出的 $s_1$、$s_2$、$out$ 为什么一定要写 HBM?不能留在寄存器 / shared memory / L1 吗?**
    - **先纠正一个前提**:在**前向 kernel 内部**,它们**确实**待在寄存器里(所以 fwd 只有 1 次读 $x$);写 HBM 是**额外**为了"留给反向用" ✓ —— 问题于是变成"反向为什么不能直接从寄存器/片上拿" ✓
    - **原因 1:片上状态不跨 kernel launch 存活**。前向与反向是**两次不同的 kernel 启动**;kernel 退出时,寄存器与 shared memory 随 block/线程一起销毁(它们是 SM 的执行资源,不是持久存储)⇒ 要在反向里用到,只能先落到 HBM ✓
    - **原因 2:L1/L2 是缓存,不是存储**。① L1 每 SM 只有约 192 KB(与 shared 共用一块 SRAM)、L2 约 40 MB(A100),内容随时会被别的数据流替换,**没有任何保留保证**;② 反向按**逆序**回放,轮到第 1 层时它的激活早被后续层挤出缓存 ✓;③ 反向的 block 还可能被调度到**另一个 SM**,L1 更不相干 ✓
    - **原因 3:容量差两个数量级**。算个例子:一层 $B=8$、$T=1024$、$C=1024$、bf16 ⇒ 单个激活张量 $8\times1024\times1024\times2\text{B}=16$ MB,存 $s_1,s_2,out$ 就是 48 MB/层;而整卡片上存储 = 108 个 SM ×(256 KB 寄存器 + 192 KB shared/L1)≈ 47 MB,再加 L2 40 MB ≈ 87 MB ⇒ **全片片上空间只够放一两层**,而模型有几十层、激活总量是 GB 级 ✓
    - **原因 4(根本原因):前向时刻还算不出反向**。反向需要 $\bar y_3=dout$,而 $dout$ 要等**这一层之后的所有层**(一直到 loss 再反传回来)都算完才存在 ⇒ 前向结束时它还不存在 ⇒ **不可能"前向时顺手把反向算掉"** ⇒ 激活只能放到"将来还找得到"的地方 ⇒ 只有 HBM 够大、够持久 ✓
    - **什么情况下可以不放 HBM**:① **推理**(没有反向)⇒ 算子融合把整条链放进一个 kernel,中间量全在寄存器(P30–P33 的 fusion)✓;② **重算 / checkpoint** ⇒ 只存 $x$(或每段一个 checkpoint),反向时重算(P36)✓;③ **可逆网络**(RevNet / reversible transformer)⇒ 反向时用下一层的激活**重建**上一层的,不存激活 ✓;④ 层内的**小中间量**(某个 tile)本来就留在寄存器/shared,不落 HBM ✓
    - **一句话**:寄存器与 shared memory 是"**执行过程中的临时工作台**",HBM 才是"**跨 kernel、跨时间**的存储";前向与反向被时间隔开,所以激活必须落到唯一够大又持久的 HBM 上 —— 这正是 P30 "工厂/仓库"比喻的意思 ✓

- [x] **Q16(p37)｜"burst"具体是什么?**
  > 原问(还原):这里 burst 的具体含义和详细解释。
  - **一句话**:DRAM 内部是"先激活整行、再按列取数",读**一个字节**和读**一整行**的固定开销几乎一样 ⇒ 硬件干脆**一次给你一大块**(burst),这也是 GPU 内存事务是 32B/128B 而不是 4B 的原因 ✓
  - **物理原因**(讲义原话):"burst mode comes from the slow per-row copy to the sense amplifier" —— 把一整行电荷搬到读出放大器(行缓冲)很慢,但一旦搬完,同一行里连续取数很快 ✓
  - **工程含义**:一次事务有固定成本 ⇒ 让 32 个线程的访问落在**同一个 burst** 里就能"一次事务取 128B" ⇒ 有效带宽×32 ✓(Q18 的 coalescing)✓

- [x] **Q17(p37)｜amplifier 指什么?DRAM 到底怎么读数据?**
  > 原问(还原):amplifier 指的是啥?具体是如何从 DRAM 上读取数据的?根据这幅图解释下。
  - **amplifier = sense amplifier(读出放大器)**:DRAM 每个 bit 是一个小电容,电荷量极小,必须由 sense amplifier **放大**才能读成 0/1 ✓(图里那一排三角形就是它)
  - **读流程(三个物理动作)**:① 行地址 ⇒ 把整行电荷冲到 sense amplifier 阵列(**行激活**,慢);② 行数据就存在**行缓冲**里;③ 列地址 ⇒ 从行缓冲里选出字节输出 ✓
  - **两个后果**:① 同一行内的连续访问快(行缓冲命中 ✓);② **换行很贵**(需要 precharge + 再激活)⇒ 顺序访问远快于随机/跨行访问 ✓
  - 这也解释了矩阵按行遍历与按列遍历的性能差异:按列遍历等于"每次都换行" ✗(Q19)✓
  - **追问(2026-10-20)｜"Burst mode comes from the slow per-row copy to the sense amplifier" 这句话到底在说什么?**
    - **先拆语法**:"**burst mode**(突发传输)**来自** —— **per-row(按行)、slow(慢)、把整行拷贝进 sense amplifier** 这一步" ✓。意思是:**burst 不是随便定的协议,而是为了摊薄"开一行"的固定成本** ✓
    - **一次行激活到底发生了什么**:① 所有 bitline 先**预充**到中间电压,然后断开预充电路;② 抬高目标行的 **wordline** ⇒ 该行**每个**存储电容把微小电荷倒到各自的 bitline(bitline 电容约为单元电容的 10 倍,所以电压变化极小);③ 每条 bitline 配一个 **sense amplifier**(一对交叉耦合的反相器),靠正反馈把微小差值放大成 0/1 —— **整行的所有单元同时被读出并锁存** ⇒ 这就是"把整行 copy 进读出放大器",而这份锁存内容就是 **行缓冲(open row / row buffer)** ✓
    - **为什么说它"slow"**:这一趟要经历"预充 → 行激活(几十纳秒量级)→ 读出放大 → 写回(读出是破坏性的,顺手恢复)→ 关闭行再预充";这些延迟(tRCD、tRP 之类)是**按行**收的,**每开一行付一次** ✓
    - **摊薄的算术(所以要 burst)**:行一旦开着,再从**同一行**取别的列就很快 —— 经典参数下"第一个读"要 50–60 ns(tRAC),同一行内的后续读只要 20–25 ns(tPC),老的 5-2-2-2 时序就是"第一个 5 拍、之后每 2 拍" ✓ 于是:一次命令只搬 4 B,那么几十纳秒的开行成本就摊在 4 B 上,亏得离谱;一次命令连续搬一串字(burst,如 BL8)⇒ 开行成本摊到 32–64 B 甚至更多 ✓ 粗算:开行 30 ns + 传 128 B 约 2 ns ⇒ 每字节 0.25 ns;只传 4 B 则是 30 ns / 4 B = 7.5 ns/B,**差 30 倍** ✓
    - **burst 的定义就是这个**:给一次 READ/WRITE 命令,DRAM 内部按列地址递增**连续输出一串字**(burst length,BL;DDR3/4/5 常见 BL8),不必每个字都发一次命令 ⇒ 省掉"命令/地址 + 开行"这些固定开销 ✓
    - **落到 GPU 上**:内存子系统的最小事务是 **32 B 的 sector / 128 B 的 cache line**;一个 warp 的 32 条 lane 各读 4 B 且地址连续 ⇒ 正好 128 B 一次搬完(Q18/Q20)✓;若 32 条 lane 读的地址相距很远 ⇒ 32 次事务,每次"只用 4 B 却搬了 32 B" ⇒ 这就是 coalescing 的意义 ✓
    - **另一个推论**:同一行内的访问(行缓冲命中)远快于跨行访问 ⇒ **顺序访问远快于随机/跨行访问** ⇒ 这是 Q19"行主序 vs 列主序"性能差异的物理根源 ✓
    - 参考:[Wikipedia: DRAM](https://en.wikipedia.org/wiki/Dynamic_random-access_memory)("All storage cells in the open row are sensed simultaneously, and the sense amplifier outputs latched";tRAC 与 tPC 的对比);讲义 P37 引的那段 YouTube 视频讲的也是这个 ✓
  - **追问(2026-10-20)之二｜我的理解是"先定位行 → 整行进行缓冲 → 再按列取",所以行内快、跨行慢 —— 对吗?**
    - **对,这个理解抓住了要点** ✓ 只补三处更精确的说法:① 慢的是"**打开一行**",不是"读一行" —— 行一旦开着,行内任意列都快;② "读出一整行"的物理动作是**整行同时被 sense amplifier 放大并锁存**(锁存内容就是行缓冲),不是"搬进另一块内存";③ 跨**行**慢,但跨 **bank**(存储体)未必慢 —— 不同 bank 的行可以同时开着 ✓
    - **物理图景(一眼看懂布局)**:一个 bank 是**二维网格**:横向是 **wordline(行)**,一条 wordline 横跨这个 bank 的**所有 bitline**;纵向每条 bitline 上挂着一串电容单元。**行地址**选哪一条横向线,**列地址**选这一行里哪几位 ✓ 所以一次访问的天然顺序就是"**先行后列**" ✓
    - **图书馆类比**:把 DRAM 想成"一墙书架,每层隔板 = 一行"。想拿某层上的某本书:管理员必须先把**整层隔板抽到阅览台**上(开行,慢,几十纳秒);放到台上后,从这层挑**任意一本**都很快(行内访问,几纳秒);要换到另一层,得把当前这层**推回去、再抽出新的一层**(预充 + 再开行,又一次慢动作)✓
    - **三种访问的快慢**:
      - **行内连续**(row-buffer hit):只发列地址 ⇒ 快(经典参数约 20–25 ns / tPC)✓
      - **换行(同一个 bank)**:先**预充关闭**当前行,再**激活**新行 ⇒ 多付约 25–30 ns;在 2 GHz 的 GPU 上相当于**空转 50–60 个周期** ✓
      - **换 bank**:别的 bank 的行可以一直开着 ⇒ 能用 bank 级并行躲掉一部分延迟 ✓
    - **所以"整行读出来"是必然**:列地址只是"从已锁存的整行里挑几位" —— 你哪怕只要 1 字节,也已经付了"开行 + 整行放大"的钱 ⇒ 这就是 burst 的由来(见上一条追问)✓
    - **对程序员的两个直接推论**:① **顺序访问远快于跨行/跨列访问**:按行遍历(row-major)走的是行内连续元素,按列遍历等于"每一步都换行" ⇒ 这是 Q19 性能差异的根源 ✓;② 矩阵维度与 stride 决定"命中同一行的比例" ⇒ 这也是 Q23 里 padding / 对齐有用的原因之一 ✓

- [x] **Q18(p38)｜coalesced 的具体含义是什么?**
  > 原问(还原):这里 coalesced 的具体含义,代表的是什么意思?
  - **定义**:一个 warp 的 32 个线程的内存访问**落在同一段(或少数几段)连续地址**里 ⇒ 硬件把它们**合并成一次内存事务** ✓
  - **反之(uncoalesced)**:32 个线程访问 32 个相距很远的地址 ⇒ 要发 32 次事务 ⇒ 大部分带宽浪费在"只用了 4 字节却搬了 128 字节" ✗
  - **记忆**:coalescing 减少的不是"你要的数据量",而是"实际搬的字节数";它直接决定有效带宽 ✓
  - **追问(2026-10-20)｜warp 里的 32 个线程取数是一起进行的吗?能理解成"数据各不相同、指令相同"吗?**
    - **分两层答**:① **指令层**:是"一起"的 —— 一条 `LDG` 指令只发射一次,32 条 lane 各自给出自己的地址,同时进入访存流水线 ✓;② **事务层**:是不是"一次拿全"取决于**地址是否连续**,由访存合并器(coalescer)把 32 个地址归并成若干个 32 B sector / 128 B line 的请求 ✓
    - **三种地址分布的账**(每条 lane 读 4 B、共 128 B 有用数据):
      - **完全连续**:落进 1 条 128 B line(4 个 32 B sector)⇒ **1 个请求**,利用率 100% ✓
      - **跨 2 条 line**:2 个请求,搬 256 B ⇒ 利用率 50% ✓
      - **32 个地址各在一条 line 上**:最多 32 个请求,搬 $32\times32\text{B}=1024$ B ⇒ 利用率 **12.5%** ✓
    - **所以"一起"的准确含义**:一条指令、一次发射、同一组事务 —— 但**事务条数随地址局部性变化**,这正是 coalescing、对齐(Q23)、tiling(Q21)存在的理由 ✓
    - **每条 lane 还能一次读更多**:`LDG.64/128` 让每条 lane 读 8/16 B ⇒ 一条 warp 指令一次最多搬 $32\times16\text{B}=512$ B(4 条 line)✓ 这是"向量化 load"提高带宽利用率的原因 ✓
    - **延迟怎么藏**:load 的数据没回来,warp 就 **stall**;scheduler 立刻换别的 warp 上 ⇒ 所以需要几十个 warp 同时在飞(Q3 的 throughput)✓;另外把独立的 load 提前发出去(循环展开、多条 load 在飞)能增加 **memory-level parallelism**,让延迟重叠 ✓
    - **第二问:对,这就是 SIMT** ✓ —— "**同一条指令、不同的寄存器/地址/数据**"正是 SIMT 的定义 ✓ 补三点:① 同一 warp 内 PC 相同,"指令相同"是硬件强制的;② 一旦出现按 lane 数据分叉的分支,这个"相同"就被打破(divergence,Q10),硬件只能分时走不同路径;③ Volta 之后每条 lane 有独立 PC(independent thread scheduling),但每个 scheduler 每周期仍只发**一条**指令 ⇒ "一条指令喂 32 条 lane"的本质不变 ✓

- [x] **Q19(p39)｜coalesce 是什么?row-major 指什么?图里在讲什么?**
  > 原问(还原):coalesce 是啥意思?这里具体讲的是什么?row-major-matrices 是否指的是在内存中按照行组织的?也就是上面的右图?
  - **coalesce = 合并**:把 warp 内多个线程的小访问合并成一次大事务(见 Q18)✓
  - **row-major(行主序)**:矩阵在内存里**先存第 0 行、再第 1 行……**(同一行的元素地址连续)✓ —— 你说的"右图"如果画的是"行内连续"就对 ✓;C 语言默认就是 row-major ✓
  - **讲义在讲的"坑"**:对 row-major 矩阵,**让线程沿行移动反而不 coalesced** —— 若一个 warp 的 32 个线程分别处理"同一列的不同行",要读的地址间隔等于**一整行** ⇒ 32 次事务 ✗;反之让线程沿**列**方向(同一行内相邻元素)分配 ⇒ 地址连续 ⇒ 一次事务 ✓
  - 一句话:**coalescing 看的是"同一时刻各 lane 的地址是否连续"** —— 也就是"**同一时刻 lane 铺在哪个轴**"要和"内存沿哪个轴连续"对齐 ✓(每条 lane 自己的扫描方向是次要的,见下面的追问)
  - **追问(2026-10-20)｜P39 的两幅图到底画了什么?为什么"沿行移动"反而不 coalesced?**
    - **先把两个词钉死**:① **row-major(行主序)**:内存里**先放第 0 行、再第 1 行**……同一行的元素地址连续 ⇒ 右图**底部那排平铺的** M₀,₀…M₃,₃ 就是它 ✓(顶部 4×4 网格只是逻辑视图)② **coalesce 看的是"同一时刻 32 条 lane 的地址集合"**,**不是**每条 lane 自己走的那条轨迹 ✓ —— 这是理解这三张图的钥匙 ✓
    - **(A) not coalesced**:Thread 1 负责**一行**、Thread 2 负责另一行,各自**沿行**从左往右扫 ⇒ 单看每个线程,它自己的地址确实连续;但**同一时刻**,两条 lane 的地址相差**整整一行**(WIDTH 个元素)⇒ 一个 warp 里 32 条 lane 散落在 32 行上 ⇒ 每条都落在**不同的 burst** 里 ⇒ 要发很多次事务 ⇒ 不 coalesced ✗
    - **(B) coalesced**:Thread 1、Thread 2 各负责**一列**、沿**列**往下扫 ⇒ 同一时刻所有 lane **在同一行、不同列**上 ⇒ 地址连续 ⇒ 一个 burst 就能覆盖 ⇒ coalesced ✓
    - **右图在说什么**(把 **(A)** 落到内存布局上,这是 P39 最直白的一张):顶部 4×4 是逻辑视图,箭头表示 kernel 里**每个线程沿自己那一行、列号递增**地扫 ✓;底部是行主序平铺的内存,每 4 格 = 一行,"**每行就是一个 burst**" ✓。看两个括号:`Load iteration 0` 里 T₀ 读 M₀,₀、T₁ 读 M₁,₀、T₂ 读 M₂,₀、T₃ 读 M₃,₀ ⇒ **这是第 0 列**(每条 lane 各在自己那一行)⇒ 4 个地址落在 **4 个不同的 burst** 上 ⇒ **4 次事务**,每次搬一整个 burst 却只用 4 B ✗;`Load iteration 1` 里 T₀..T₃ 读 M₀,₁、M₁,₁、M₂,₁、M₃,₁ ⇒ **第 1 列**,同样 4 次事务 ✗ ⇒ 右图画的是"**每线程负责一行**"的坏写法 ✓
    - **一个反直觉点**:右图里**每个线程自己的**地址其实连续(T₀ 依次读 M₀,₀→M₀,₁→M₀,₂→M₀,₃,全在同一个 burst 内),但**同一时刻整个 warp 的**地址跨了 4 行 ⇒ **per-thread 的局部性好,不等于 warp 的 coalescing 好** ✓ —— 讲义那句 "reads the entire vector at each step" 说的就是:一次访问的粒度是整段(一个 burst = 一整行向量);(A)/右图 里这段只用了 4 B(浪费),(B) 里这一整段正好被 32 条 lane 用满(划算)✓
    - **回答"为什么第一次不是读 M₀,₀..M₀,₃"**:那样写就变成 **(B) 的映射**了 —— 让 T₀..T₃ 各负责**一列**,第 0 次迭代它们一起读 M₀,₀..M₀,₃(连续,1 次事务)✓。所以你的直觉正是**修法**;而图中 iteration 0 读 M₀,₀、M₁,₀、M₂,₀、M₃,₀,恰恰是"每个线程负责一行"(`for j: M[tid][j]`)这种最常见写法的后果 ✓
    - **数值算一下**(1024×1024、float、每元素 4 B):一行 4096 B = 32 个 128 B line ✓。**(A)**:32 条 lane 各在一行 ⇒ 32 个 32 B sector,搬 $32\times32\text{B}=1024$ B、只用 128 B ⇒ **12.5%** ✓;**(B)**:32 条 lane 在同一行、32 个相邻列 ⇒ 128 B 正好一条 line ⇒ **100%** ✓
    - **落到矩阵乘上**:若"一个线程负责输出的某一行"、warp 的 lane 沿 $i$ 铺开(就是 (A) 的情形),那么取 $A_{i,k}$ 时 32 条 lane 跨 32 行 ⇒ 不 coalesced ✗。解法正是 Q21 的 tiling:让线程**按行**协作把 $A$、$B$ 的 tile 搬进 shared memory(这一步地址连续、coalesced ✓),之后在片上反复读 tile ✓
  - **追问(2026-10-20)之二｜能不能理解成"整个 warp 就是在读一个矩阵"?每个线程每次读一个元素?**
    - **大方向对,补三个限定**:① 图里为了画得下只画了 2 条 lane(右图 4 条),**真实是 32 条** ⇒ 一次 load 迭代就是 32 个元素 ✓;② 每条 lane 一次读的是**一个元素**(标量 4 B;用 `LDG.64/128` 可以一次读 8/16 B,即"一串元素")✓;③ 读到的数据进入**每条 lane 自己的寄存器**,不存在"warp 的公共寄存器" ✓
    - **"读完一个矩阵"要多次迭代**:右图的 4×4 小矩阵 = 4 条 lane × 4 次迭代(第 0 次读第 0 列的 4 个、第 1 次读第 1 列……)⇒ 迭代完覆盖整个矩阵 ✓;(A)/(B) 的差别**不在"每条 lane 读一个元素"**,而在**同一次迭代里这 32 个地址连不连续** ✓
    - **真实 kernel 里不是"一线程一元素"**:通常每个线程一次读**多个**元素(如 4 个 float,或用向量化 load),并让它们在后面的计算里**复用多次**;一个矩阵也通常由**很多 warp / 很多 block** 分担,每个只负责一个 tile ✓ —— "一线程一元素"只是最好懂的示意图;真那么写,每算一次乘加(2 FLOP)要读两个元素(约 8 B)⇒ 算术强度只有 0.25 FLOP/B,算力被带宽拖死 ✓
    - **一句话**:warp 的执行单位是"**一条指令 × 32 条 lane,每条 lane 各读各的地址**";是"一堆指令 + 多次迭代"合起来才覆盖一个矩阵(toy 例子一个 warp 就够,真实矩阵要很多 warp 分工)✓
  - **本质理解(2026-10-20 小结)｜同一时刻 32 条 lane 要落在"能被一次读走的一小段连续内存"里,不同时刻可以换到别的段**
    - **一句话**:一条 warp 指令 = 32 条 lane 各出**一个地址**;coalescing 的本质就是**让这 32 个地址落在尽可能少的连续段里**,用一次(或少数几次)大事务把 32 份数据全搬回来,而且每一字节都被用上 ✓
    - **判据的准确形式**:是"**连续**",不是"**同一行**" ✓。行主序下同一行的列连续,所以"同一行"只是示意图里的代理条件;真实硬件上只要 32 个地址连成一段(理想:落在 1 个 32 B sector / 一个 128 B line 内),**哪怕跨了几行也算 coalesced** ✓;反过来,同一行内但"隔一个取一个"照样要多次事务 ✗
    - **时间维度是自由的**:同一时刻要连续,**不同时刻完全可以在不同行** —— 顺序遍历时每次换到下一段,每段都是一次事务用满;而且顺着行往下走还能吃到**行缓冲命中**(Q17),比跳着走更快 ✓
    - **为什么是"32 个元素"而不是"32 次访问"**:指令只发射一次(取指/译码 1 次),32 条 lane 的操作数各自从自己的寄存器来,访存单元再把它们合成若干事务 ⇒ **控制开销 1/32、事务数只由连续性决定** ✓(这就是 Q8 的 SIMT 和 Q18 的 coalescing 拼在一起)
    - **换算成字节**:每条 lane 读 4 B ⇒ 一个 warp 一次 128 B;读 16 B(`LDG.128`)⇒ 512 B。所以"理想情况"是**128 B 对齐的连续 128 B(或 512 B)被这一个 warp 用满** ✓;不对齐就会跨到两条 line,多一次事务(Q23)✓
    - **一句话记住**:同一时刻看"**32 个地址是否挤在一小段连续内存里**",不同时刻看"**是否顺着内存往下走**" ✓
    - **术语澄清(五个粒度,从小到大)**:
      - **元素**:一条 lane 一次读的量(4 B;向量 load 为 8/16 B)✓
      - **sector / line(GPU 侧的事务粒度)**:32 B sector、128 B line —— **coalescing 说的"连续段"就是它** ✓
      - **DRAM burst**:一条 READ 命令连续吐出的 BL 个字(BL8 常见,约 32–64 B) —— "burst mode" 说的是这一层 ✓
      - **DRAM 行(page)**:1–8 KB,**单位是"开一次行"**(Q17)✓
      - ⇒ **行(1–8 KB)≫ 事务(32–128 B)≈ burst(32–64 B)≫ 元素(4 B)**:一行里有很多个 burst ⇒ **"同一行"远不等于"同一次事务"** ✓
    - **所以"同一行还不够"**:即使 32 条 lane 都在同一行,只要它们分散在行内不同的 sector(例如同一行里以 128 B 为 stride 取 32 个元素(行宽 4096 B,正好占满一行)⇒ 32 个不同 sector),就仍是 **32 次事务** ✗;我们要的是"32 条 lane 挤进同一个(或少数几个相邻的)sector/line" ✓
    - **"大事务"到底指什么**:指一次**访存事务**(32 B sector / 128 B line);它通常由一次或几次 **DRAM burst** 完成 ⇒ 两者是"**请求**"与"**底层搬运**"的关系(不是同一个东西,但"一次搬一整段"的直觉是对的)✓
  - **追问(2026-10-20)之三｜"事务"和"burst"到底差在哪?GPU 不是每次都读一个 burst 吗?BL 又是什么?**
    - **结论先说**:两者在**不同层** —— **事务(transaction)是"请求粒度"**(SM / cache 向内存系统要一段,GPU 上量化为 32 B sector / 128 B line),**burst 是"底层搬运粒度"**(DRAM 收到一条 READ 命令后,在总线上连续吐出 BL 个字)✓ 一次事务可以对应**一到几次** burst ✓
    - **BL(burst length)= 一次命令连吐多少个"字"**:DDR 的 READ 命令只给**起始列地址**,DRAM 内部按 BL 自动递增连发;每个"字" = 总线宽度(例:DDR4 单通道 64 bit = 8 B)⇒ BL8 一次命令搬 $8\times8\text{B}=64$ B ✓ 常见 BL4/BL8;DDR5 的 32-bit 子通道配 BL16 ⇒ 也是 64 B ✓ HBM 的每个伪通道是同量级(32–64 B)✓
    - **谁负责哪一层**:
      - **事务**:由 **SM 的访存单元 + L1/L2** 产生并统计 —— 一条 warp 指令的 32 个地址被合并成若干 sector / line 请求(profiler 里的 sector / request 计数就是它)✓
      - **burst**:由 **内存控制器 + DRAM 颗粒**完成 —— 控制器把请求翻译成"激活行 → 发 READ(带列地址与 BL)→ 总线上连发 BL 个字"✓
    - **所以"GPU 每次读一个 burst"哪里不准确**:① 一条 warp 指令可能产生**多个事务**(地址不连续、跨行、不对齐都会)✗;② 一个事务在 DRAM 侧又可能拆成**多个 burst**(如 128 B line 落在两个 64 B 通道上 ⇒ 2 次 burst)✓;③ 反过来,一个 32 B sector 的请求也可能只用到 burst 的一部分(靠 mask)✓
    - **为什么区分它们对你有用**:你能控制的只有**地址**;能优化的计数是**事务 / sector 数**(32 B 也是"浪费"的计量单位);burst 是控制器的事,你只能靠"连续 + 对齐"让它每次都满载 ✓
    - **类比**:事务 = 你向仓库下的**订单**(要哪一段,32 B 或 128 B);burst = 仓库内部用叉车搬出的**一托盘**(BL × 总线宽度)。一张订单可能对应 1~几托盘:订单是你关心的粒度,托盘是仓库内部的搬运粒度 ✓
    - **一张对照表**:

      | 层 | 谁产生 / 谁决定 | 典型粒度 | 你在哪看到它 |
      | --- | --- | --- | --- |
      | 元素 | 你的代码(每条 lane) | 4 B(或 8/16 B) | 变量 / 张量 |
      | 事务(sector / line) | 访存合并器 + L1/L2 | 32 B / 128 B | profiler 的 sector / request 计数 |
      | burst(BL × 位宽) | 内存控制器 + DRAM | 32–64 B | DRAM 时序与带宽分析 |
      | 行(page) | DRAM 颗粒 | 1–8 KB | "开行"成本(Q17) |

  - **追问(2026-10-20)之四｜"一条 warp 指令"是谁执行?一条指令最少几个事务 / 几次 burst?该优化哪个数?**
    - **术语纠正**:不是"32 个 warp",而是"**1 个 warp = 32 条 lane(线程)**";"**一条 warp 指令**"= **一条指令被 1 个 warp 执行**,32 条 lane 各用自己的寄存器操作数 ✓(SM 里可以同时驻留几十个 warp,那是另一回事)✓
    - **事务数取决于"覆盖了几条 line / 几个 sector"**。32 条 lane 各读 4 B(共 128 B)时:
      - **连续且 128 B 对齐**:正好 1 条 line = **4 个 32 B sector** ⇒ 按 line 请求计 1 次、按 sector 计 4 个 ⇒ 利用率 100% ✓
      - **连续但不对齐**(例如整体偏移 4 B):跨 2 条 line ⇒ **2 次事务** ⇒ 搬 256 B 用 128 B,利用率 50% ✓
      - **分散**:最多 **32 次**(每个 32 B sector 一次)⇒ 利用率 12.5% ✓
      - **向量化**(`LDG.128`,每条 lane 16 B):跨度 512 B = **4 条 line** ⇒ 4 次事务,但 512 B 全部有用 ⇒ 利用率 100% ✓
    - **能不能"只包含一次 burst"**:只有当整段跨度**不超过一个 burst**(32–64 B)时才行;128 B 的 line 一般会拆成 **2 个 64 B burst**(或落在两个通道上各一次)⇒ 现实中通常是"1 次事务 ⇒ 2~4 次 burst",不是 1 次 ✓
    - **优化目标要改口径**:不是"事务数越少越好",而是"**每次事务都满载**" —— 核心指标是**浪费率 = 实际抓取字节 / 有用字节**(等价地:每个 32 B sector 里有多少字节被用上)✓ 4 次事务搬 512 B 全部用上,远好于 1 次事务搬 128 B 只用 32 B ✓
    - **burst 数需要优化吗**:**不能直接优化** —— 它由内存控制器、通道交织与颗粒决定;你能做的只是"连续 + 对齐 + 向量化",让每次事务满载 ⇒ burst 自然被用满 ✓(零散访问则每次 burst 大部分被 mask 掉)✓
    - **一句话**:把"**同一时刻 32 条 lane 的地址**"压进尽量少的 sector/line,并让每条 lane 一次多搬一点(向量化);burst 是控制器的事,只会跟着受益 ✓

- [x] **Q21(p41)｜按图把 tiling 算法一步步展开:$M_{0,0}$ 是元素还是子矩阵?tile 是什么?**
  > 原问(还原):按照这个例子,详细解释下这个算法。不省略地展开下具体的步骤。这里的 $M_{0,0}$ 指的是一个元素,还是左上角的这个子矩阵?每个 tile 指的是什么?
  - **$M_{0,0}$ 是子矩阵(不是元素)**:$M_{i,k}$ 表示"第 $i$ 个行块、第 $k$ 个列块"那个 $T\times T$ 的子矩阵 ✓(左上角那块就是 $M_{0,0}$ ✓);**tile = 这样一个子矩阵块**,加载单位是 tile ✓
  - **算法**(算 $P=MN$,块大小 $T$,一个 block 负责一个输出 tile $P_{i,j}$):
    1. `P_local = 0`(放在寄存器里累加);
    2. **for $k=0..K/T-1$**:① 协作把 $M_{i,k}$ 与 $N_{k,j}$ 从 global 拷到 shared memory(每个线程拷一部分,且要 coalesced,见 Q20)② `__syncthreads()` ③ 每个线程算自己负责元素的部分和:$P_{i,j}\mathrel{+}=M_{i,k}N_{k,j}$ ④ `__syncthreads()`(免得下一轮覆盖未读完的数据);
    3. 算完所有 $k$ 后,把 $P_{i,j}$ 写回 global ✓
  - **为什么省**:$M_{i,k}$ 被同一行块内的**所有**列块复用;$N_{k,j}$ 被同一列块内的所有行块复用 ⇒ 每个输入从 global 读 $N/T$ 次(而不是 $N$ 次)⇒ 总体**减少 $T$ 倍** ✓(P42 原话)✓
  - 讲义 P41 第 3 步写作 "Load the $M_{0,0}$ and $N_{2,0}$ tile":按"以 tile 首元素命名"的约定,沿 $k$ 换下一块应该是 **$M_{0,2}$ 与 $N_{2,0}$**($M_{0,0}$ 应是笔误)✓
  - **追问(2026-10-20)｜P40 那句 "not coalesced, and repeated" 什么意思?切块是 4 个子矩阵吗?为什么 tiling 后既走 shared 又能 coalesced?**
    - **先看 P40 在算什么**:图里 4 个线程各负责一个输出元素 $P_{i,j}=\sum_k M_{i,k}N_{k,j}$(右侧 "Access order" 表:thread0,0 依次算 $M_{0,0}N_{0,0}$、$M_{0,1}N_{1,0}$、$M_{0,2}N_{2,0}$、$M_{0,3}N_{3,0}$ ✓)
    - **"repeated"(重复读)**:同一个 $M$ 元素被**同一行的所有输出**用到 —— 表里 $M_{0,0}$ 同时出现在 thread0,0 和 thread0,1 的序列里;同样 $N_{1,0}$ 同时出现在 thread0,0 和 thread1,0 的序列里 ✓。推广到 $N\times N$:每个输入元素被读 **$N$ 次**,总全局读 $\propto 2N^3$(P42 原话)✓
    - **"not coalesced"(不合并)**:在同一个 $k$ 上,不同 lane 要的地址互不相邻 —— 要 $M_{i,k}$ 就得跨行(间隔一整行),要 $N_{k,j}$ 时同一线程沿列走(行主序下 stride = 行宽)⇒ 一个 warp 的 32 个地址散成很多段。**数值**:1024×1024、float,一列里相邻两行相差 4096 B ⇒ 32 条 lane 读同一列的 32 个元素 = **32 次事务**,只用 128 B 的 32 分之一 ✓
    - **切块方式(P41 图)**:**$M$ 和 $P$ 都是 4×4,各切成 2×2 = 4 块**(每块 2×2 个元素,粗黑框就是块边界);**$N$ 也画在 4×4 的画布上、切成 2×2 = 4 块**,但它只有 2 列 ⇒ **只有左边 2 块有数据、右半边是空的**(每块仍是 2×2)✓ —— 图里 $P_{0,0}$(黄)、$P_{0,1}$(绿)、$P_{1,0}$(红)、$P_{1,1}$(蓝)正好是左上角那个输出 tile 的 4 个元素 ✓
    - **数一下 $M_{0,0}$ 被访问几次**(讲义小例子:$N=4$、$T=2$):① 朴素版被 4 个输出($P_{0,0},P_{0,1},P_{0,2},P_{0,3}$)各用一次 ⇒ **全局读 4 次**;② tiling 后 $M_{0,0}$ 属于 $M$ 的 tile (0,0),该 tile 被 block-row 0 的**每个 block** 各搬一次,而 block-row 0 有 $N/T=2$ 个 block ⇒ **全局读 2 次**;③ 在每个 block 内部,它从 shared 被用 $T=2$ 次(分别算这个 block 的两列输出)⇒ **shared 读 4 次**;④ 合计:**总"使用"仍是 4 次,但只有 2 次走 global** ✓ —— 这正是 P42 的 $N/T$;若 $T=4$(一块覆盖全部列),$M_{0,0}$ 就只从 global 读 **1 次** ✓
    - **完整伪代码**(一个 block 负责一个 $T\times T$ 的输出 tile;`blockDim = (T, T)`,取 $T=32$ 时正好一个 warp 一行):

      ```c
      // C[M][N] = A[M][K] @ B[K][N]；tile 大小 T×T
      __global__ void matmul_tiled(const float* A, const float* B, float* C, int M, int N, int K) {
          __shared__ float As[T][T];                 // A 的一个 tile（片上）
          __shared__ float Bs[T][T];                 // B 的一个 tile（片上）
          int tx = threadIdx.x, ty = threadIdx.y;     // 0..T-1
          int row = blockIdx.y * T + ty;              // 本线程负责的输出行
          int col = blockIdx.x * T + tx;              // 本线程负责的输出列
          float acc = 0.0f;                           // C[row][col] 的累加器（寄存器）
          for (int k0 = 0; k0 < K; k0 += T) {         // 沿 K 方向，一块一块推进（"phases"）
              As[ty][tx] = A[row * K + (k0 + tx)];    // 协作搬运：线程 tx 连续 ⇒ 地址连续 ⇒ coalesced
              Bs[ty][tx] = B[(k0 + ty) * N + col];    // 同上：同一行的相邻列 ⇒ coalesced
              __syncthreads();                        // 等整个 tile 到齐（也防止上一轮未读完就被覆盖）
              for (int kk = 0; kk < T; ++kk)          // 在片上做部分和：读 shared，不读 global
                  acc += As[ty][kk] * Bs[kk][tx];
              __syncthreads();                        // 确认大家都读完，再进入下一块
          }
          C[row * N + col] = acc;                     // 写回一个元素
      }
      ```

    - **用手推一遍讲义的小例子**($T=2$,一个 block 4 个线程 thread0,0..thread1,1,负责 $P$ 的左上 tile):
      - **phase $k=0$**:装入 $M$ 的 tile $\begin{bmatrix}M_{0,0}&M_{0,1}\\M_{1,0}&M_{1,1}\end{bmatrix}$ 与 $N$ 的 tile $\begin{bmatrix}N_{0,0}&N_{0,1}\\N_{1,0}&N_{1,1}\end{bmatrix}$ ⇒ 算部分和:$P_{0,0}\mathrel{+}=M_{0,0}N_{0,0}+M_{0,1}N_{1,0}$;$P_{0,1}\mathrel{+}=M_{0,0}N_{0,1}+M_{0,1}N_{1,1}$;$P_{1,0}\mathrel{+}=M_{1,0}N_{0,0}+M_{1,1}N_{1,0}$;$P_{1,1}\mathrel{+}=M_{1,0}N_{0,1}+M_{1,1}N_{1,1}$ ✓
      - **phase $k=1$**:装入 $M$ 的右 tile $\begin{bmatrix}M_{0,2}&M_{0,3}\\M_{1,2}&M_{1,3}\end{bmatrix}$ 与 $N$ 的下 tile $\begin{bmatrix}N_{2,0}&N_{2,1}\\N_{3,0}&N_{3,1}\end{bmatrix}$ ⇒ 再加同样的 4 项 ⇒ 得到完整的 $P_{0,0},P_{0,1},P_{1,0},P_{1,1}$ ⇒ 写回 global ✓
    - **为什么"repeated reads 变成访问 shared"**:每个 tile 从 global **只搬一次**,之后这个 block 在 $k$ 循环($T$ 次乘加)里读的都是 `As/Bs` ⇒ 全局读次数从 $N$ 次降到 $N/T$ 次(P42);而 shared 是片上 SRAM,比 DRAM 快约 8 倍、且没有"事务/合并"的问题(只有 bank conflict)✓
    - **为什么"memory access can be coalesced"**:因为 tiling 把**两件事解耦**了 —— ① "计算需要什么"(计算阶段读的是 shared,访问模式可以随便不规则);② "怎么把 tile 搬进来"(搬运循环里线程→元素的映射**由你设计**)。只要让 `tx` 映射到**同一行的相邻列**(上面 `As[ty][tx] = A[row*K + k0+tx]`),32 条 lane 就是连续的 128 B ⇒ 一次 line 事务 ✓;$T=32$ 时一个 warp 正好搬一行 ✓
    - **一句话**:tiling 同时解决"**重复读**"(用 shared 复用)与"**不合并**"(把不规则的计算访问留在片上,只让规整的搬运走 global)✓
    - **"没做 tiling 就等于每次都要从 global 取吗"**:基本对,但要分两层看 ✓
      - **矩阵始终在 global(HBM)上**:tiling 并不搬动矩阵,它只是把 tile **复制**一份到片上 shared ✓
      - **逻辑上**:没 tiling 时,每个元素每次被用到都要**重新发起一次访存**(没有任何"保证复用"的地方)✓
      - **物理上**:这次访存会先查 **L1/L2 缓存**,命中就从片上拿,不命中才落到 HBM ✓ —— 所以"每次都必须从 global 读"严格说不成立 ✗
      - **但在朴素矩阵乘里大概率真的落到 HBM**:复用距离太大 —— 1024×1024 float 的一个矩阵就有 4 MB,远超 L1(每 SM 约 192 KB),也接近/超过 L2(约 40 MB);等同一元素被再次用到时,它早被别的数据挤出缓存 ✓
      - **这正是"靠 cache"与"靠 tiling"的差别**:cache 是**硬件自动、无保证**;shared 是**程序员显式、可保证** ⇒ 把复用放进 shared,global 读才能稳定降到 $N/T$ ✓
      - **别把两件事混了**:coalescing 与 tiling 正交 —— 即使不 tiling,连续访问照样能合并成一次事务(Q20);tiling 解决的是"**重复读**",不是"合并" ✓

- [x] **Q22(p43)｜$256\times256 @ 256\times257$ 为什么产生大量空白 tile?为什么不能跳过空白?**
  > 原问(还原):为啥这里 $256\times256 @ 256\times257$ 的矩阵运算,就会产生这么大的空白 tile?为啥不能空白的就不 tile 了?我不理解底层原理。
  - **算一下**:输出是 $256\times257$;若 tile 是 $256\times128$ ⇒ 行块数 $\lceil256/256\rceil=1$、列块数 $\lceil257/128\rceil=3$ ⇒ 共 **3 个 tile**,覆盖 $256\times384$ 的网格 ⇒ **127 列是空的**,利用率约 $257/384\approx67\%$ ✓;而 $256\times256$ 恰好 2 个 tile、零浪费 ✓
  - **为什么不能"空白就不 tile"**:① **grid 大小与 tile 形状在 kernel 启动前就固定**(静态调度),每个 block 跑同一份代码、同样大小;② 编译器/运行时无法"只为有数据的部分单独生成不同形状的 block" ⇒ 边缘 block **仍会被启动、占一个 SM 的执行槽**,只是内部线程用"越界谓词"屏蔽掉(不算/不写)⇒ 浪费的是**整块 tile 的算力** ✓
  - 这也是 P43 列的影响因素:**维度整除性**;实践解法:选 tile 大小使维度整除、或把维度 **padding** 到倍数 ✓

- [x] **Q23(p44)｜aligned 与 unaligned 两种情形是什么?为什么会发生?**
  > 原问(还原):完全没看懂这里。这两种情况是啥?为啥会出现这两种情况?分别什么情况下会引起?
  - **顶部示意**:内存被划成固定大小的 **burst 段**(图里 0–3、4–7、8–11、12–15 各一段)✓
  - **Aligned Layout(好)**:矩阵的**行宽**(一行字节数 = 列数 × 元素字节数)**正好是 burst 的整数倍** ⇒ tile 的左右边界落在 burst 边界上 ⇒ 加载一个 tile 只需读整段 burst ⇒ "One Nice Tile" ✓
  - **Unaligned Layout(坏)**:行宽不是 burst 整数倍(例如 $256\times257$ 的 bf16 行宽 514B,不是 128B 的倍数)⇒ 加载 tile 时**每一行都跨两个 burst**,只能多读一段 ⇒ "Two Bad Tiles" ✓(图上斜线就是被切开的边界)
  - **什么时候发生**:矩阵维度(或 tile 宽度)× 元素字节数**不是 32B/128B 的整数倍**时 ✓;**解法**:把行宽 **padding** 到 burst 的倍数(P44 底部那句 "have to do padding")✓
  - **意义**:这就是 P45–P48 "matrix mystery"的第一个原因 —— **1793 比 1792 慢,不只是 tile 多了,还对不齐了** ✓(P47:"Tiling has a major impact through alignment")✓

- [x] **Q24(p48)｜为何 tile 数从 98 变 120?和 SM 数量什么关系?**
  > 原问(还原):详细解释下这个例子。为啥之前是 98 个 tile,之后是 120 个?以及和 SM 的数量有啥关系?
  - **算一下**(tile $256\times128$):$1792$ 时 $\frac{1792}{256}\times\frac{1792}{128}=7\times14=98$ ✓;$1793$ 时 $\lceil1793/256\rceil\times\lceil1793/128\rceil=8\times15=120$ ✓
  - **与 SM 的关系**:**A100 有 108 个 SM** ⇒ 98 个 tile **一波就能全部启动**(98 ≤ 108)✓;120 个 tile 则要 **两波**:第一波 108 个、第二波只剩 **12 个**(96 个 SM 空转)⇒ 墙钟时间 ≈ **2 波**,而不是 $120/108\approx1.11$ 波 ✓
  - **这就是 wave quantization(波量化)**:任务数不是 SM 数的整数倍时,最后一波利用率骤降 ⇒ 性能呈"阶梯状"(P48:"What's with the periodic behavior?" ✓)
  - **缓解**:调 tile 大小使 tile 数接近 SM 的整数倍;或用 split-K、persistent kernel 做负载均衡 ✓

- [x] **Q26(p52)｜fig 1 到底在 tile 什么?给一个前向伪代码**
  > 原问(还原):根据这里的图例,详细解释下 flash attn,最好使用伪代码的形式。
  - **一句话**:fig 1 就是"**把 $S=QK^\top$ 的矩阵乘按 tile 做**"——把 $Q$ 切成**行块**(每块 $B_r$ 行),把 $K,V$ 切成**列块**(每块 $B_c$ 列),每算出一块 $S_{ij}$ 就**立刻**做 softmax、再累加 $P_{ij}V_j$,于是完整的 $n\times n$ 从不出现 ✓
  - **图里三块的含义**:① 外层循环遍历 $K/V$ 的块(沿序列方向),内层固定一个 $Q$ 块;② 每轮的 $S_{ij}=Q_iK_j^\top$ 只在 SRAM 里(形状 $B_r\times B_c$);③ 把 $S_{ij}$ 的 exp、行求和、与 $V_j$ 的乘**融进同一轮**,累加到 $O_i$ ✓
  - **难点在 softmax**:普通 softmax 要先知道**整行**最大值与总和才能归一化;分块后"整行"还没算完 ⇒ 需要 **online softmax**(Q27/P53)✓

- [x] **Q27(p53)｜online softmax 与 L5 前面讲的技巧怎么结合?为什么能提速?**
  > 原问(还原):这里能否和这个 lecture 之前讲的内容结合一下,详细说明优化点以及为啥能提速。
  - **online softmax 一句话**:维护三个量——行最大 $m$、行和 $l$、输出累加 $O$;每来一块新的 $S$:① 更新 $m'=\max(m,\ \mathrm{rowmax}(S^{new}))$ ② 用 $e^{m-m'}$ **重标定**旧的 $l$ 与 $O$(望远镜求和/telescoping)③ 把新块按 $e^{z-m'}$ 累加进去;最后 $O/l$ 即为结果 ✓
  - **对照 L5 的技巧清单**:
    - **tiling**(Q21):KQV 的三个矩阵乘块化,重复读的 $K,V$ 留在 shared memory ✓
    - **fusion**(Q14/P30):mask、exp、行求和、乘 $V$ 全在一个 kernel 里,不把 $S/P$ 写回 HBM ✓
    - **低精度**(Q11):$S/P$ 用 bf16,累加用 fp32 ✓
    - **recomputation**(Q15):反向不存 $S,P$,用 $Q,K$ 重算(P54 原话 "they recompute tile-by-tile")✓
    - **coalescing / 对齐**(Q18–Q23):块内访问连续、块宽尽量与 burst 对齐 ✓
  - **为什么提速(定量)**:朴素实现要写/读两个 $n\times n$ 矩阵($S$ 与 $P$)⇒ HBM 流量 $O(n^2)$ 量级;FA 让它们只活在 SRAM ⇒ HBM 流量降到 $O(n^2d^2/M)$($M$=SRAM 容量),**FLOPs 不变** ⇒ 在 memory-bound 的长序列上墙钟大降 ✓
  - **代价**:实现复杂(online softmax、重标定)、块大小要调($B_r,B_c$ 受 SRAM 限制)、反向要重算 ⇒ 典型的"用算力/复杂度换带宽" ✓

- [x] **Q28(p54)｜图里哪些在 SRAM、哪些在 DRAM?"not materialized in HBM" 是啥意思?**
  > 原问(还原):详细解释下这幅图。为啥一些是放在 SRAM 中,一些是放在 DRAM 中?其中 not materialized in HBM 是啥意思?
  - **放 SRAM 的**:每次 tile 的中间量——$Q_i$、$K_j$、$V_j$、$S_{ij}$、$P_{ij}$、以及 $O_i$ 的累加器 ✓ 它们**小**(塞得进片上)且**被反复使用** ✓
  - **放 DRAM(HBM)的**:$Q,K,V$ 的整体(太大)、最终输出 $O$ ✓ —— 只进出少数几次,必须常驻大容量存储 ✓
  - **"not materialized in HBM"**:那个完整的 $n\times n$ 矩阵 $S/P$ **根本不在 HBM 里生成**——不为它分配显存、也不写回/读回;它只以"一个 $B_r\times B_c$ 的块"的形式在 SRAM 里短暂存在 ✓
  - **对比朴素实现**:`S = Q @ K.T`(写 HBM)→ `P = softmax(S)`(读+写 HBM)→ `O = P @ V`(读 HBM)⇒ 两个 $n\times n$ 各往返一次 ⇒ 显存与带宽都被吃爆 ✗;FA 把这两个 $n\times n$ 抹掉 ⇒ 显存从 $O(n^2)$ 降到 $O(n)$,带宽同理 ✓
  - 一句话:**FA 的"魔法" = 让 $S/P$ 只活在 SRAM,只让 $Q,K,V,O$ 进出 HBM** ✓

**附录：FlashAttention 前向伪代码(块大小 $B_r\times B_c$)**

```python
# Q, K, V: [n, d]；分块：Q 按行切 B_r，K/V 按行切 B_c
for i in range(0, n, B_r):
    Q_i = load(Q[i:i+B_r])                  # [B_r, d]          从 HBM 读进 SRAM
    m = full(B_r, -inf)                     # [B_r]             行最大值（运行中维护）
    l = zeros(B_r)                          # [B_r]             行和（运行中维护）
    O = zeros(B_r, d)                       # [B_r, d]          输出累加器
    for j in range(0, n, B_c):
        K_j = load(K[j:j+B_c])              # [B_c, d]          从 HBM 读进 SRAM
        V_j = load(V[j:j+B_c])              # [B_c, d]
        S_ij = Q_i @ K_j.T / sqrt(d)        # [B_r, B_c]        ★ 只在 SRAM，不写回
        S_ij = mask(S_ij)                   # [B_r, B_c]        因果 / 填充掩码
        m_new = maximum(m, rowmax(S_ij))    # [B_r]
        P_ij = exp(S_ij - m_new[:, None])   # [B_r, B_c]        ★ 融合：exp 就地算
        l = l * exp(m - m_new) + rowsum(P_ij)              # [B_r]      ★ 望远镜求和：旧和重标定
        O = O * exp(m - m_new)[:, None] + P_ij @ V_j        # [B_r, d]   ★ 旧输出也重标定
        m = m_new
    O = O / l[:, None]                      # [B_r, d]          最终归一化
    write(O, O_out[i:i+B_r])                # [B_r, d]          写回 HBM
```

#### 补充 1:把 L5 的六个技巧放进同一本"账本"

一切都能落到算术强度 $\mathrm{AI}=\mathrm{FLOPs}/\mathrm{bytes}$ 这一个式子上(见 L02 roofline):硬件峰值强度约 $295$ FLOP/字节(H100 bf16),低于它就 memory-bound。于是:

| 技巧 | 改的是分子还是分母 | 收益的量级 |
| --- | --- | --- |
| control divergence | 分子不省、**有效算力**下降(等价于"花了算力只干了一半活") | 分支越散越亏 |
| 低精度 | 分母 ↓(每元素字节减半) | 最多 2× |
| fusion | 分母 ↓(中间量不落 HBM) | 与融合掉的重算/搬运用量成正比 |
| recomputation | 分子 ↑、分母 ↓ | 3 层 sigmoid 的例子里是 8 → 5 |
| coalescing | 分母 ↓(事务搬满 32B/128B) | 最多 ~32× |
| tiling | 分母 ↓(全局读 $N\to N/T$) | 约 $T$ 倍 |

**一句话**:除 divergence 是"浪费分子"外,**其余五个都在减小分母** —— 这正是 L5 主线(计算涨得比带宽快)的体现 ✓

#### 补充 2:tiling 的访存账与波量化公式

- **无 tiling**:每个输入元素被读 $N$ 次(对 $N\times N$ 的乘)→ 总读 $O(N^3)$ 个元素;tiling 后每个输入读 $N/T$ 次 → $O(N^3/T)$ ✓(P42)
- **tile 数与波数**:$G=\lceil M/T_m\rceil\cdot\lceil N/T_n\rceil$,$W=\lceil G/S\rceil$($S$ 为 SM 数)。理想工作量为 $G$ 个 tile、实际要 $W$ 波 ⇒ **利用率 $=G/(W\cdot S)$** ✓
  - $1792\times1792$、$256\times128$:$G=98$、$S=108$ ⇒ $W=1$,利用率 $98/108\approx91\%$ ✓
  - $1793\times1793$:$G=120$ ⇒ $W=2$,利用率 $120/216\approx56\%$ ✓ ⇒ 墙钟近似翻倍 —— 这就是"尺寸 +1 反而大幅变慢"的机制 ✓
- **对齐条件**:行宽 $=N\cdot\text{sizeof(dtype)}$ 要是 burst 大小(通常 128B)的整数倍。$1792\times2\text{B}=3584\text{B}=28\times128\text{B}$ ✓ 对齐;$1793\times2\text{B}=3586\text{B}$ ✗ 不整除 ⇒ 每行多读一段 burst ✓

#### 补充 3:online softmax 的推导(望远镜求和)

目标:对一行 $z_1,\dots,z_n$ 求 $l=\sum_i e^{z_i}$、$O=\sum_i e^{z_i}v_i$,最终返回 $O/l$(softmax 加权和)。

已处理前 $t$ 个,维护 $m_t=\max_{i\le t}z_i$、$l_t=\sum_{i\le t}e^{z_i-m_t}$、$O_t=\sum_{i\le t}e^{z_i-m_t}v_i$。

加入 $z_{t+1}$ 时取 $m_{t+1}=\max(m_t,z_{t+1})$,并对旧项**重标定**:$l_{t+1}=e^{m_t-m_{t+1}}\,l_t+e^{z_{t+1}-m_{t+1}}$,同理 $O_{t+1}=e^{m_t-m_{t+1}}\,O_t+e^{z_{t+1}-m_{t+1}}v_{t+1}$。

**验证**:把归纳假设代回,$e^{m_t-m_{t+1}}l_t=\sum_{i\le t}e^{z_i-m_{t+1}}$ ⇒ 加上新项正好是 $\sum_{i\le t+1}e^{z_i-m_{t+1}}$ ✓ —— 每一步只改"指数里的 max",项与项首尾相消(telescoping)⇒ 任意时刻 $O_t/l_t$ 都等于"前 $t$ 个的 softmax 加权和"(只差归一化常数)✓ 全程指数 $\le0$ ⇒ 不会上溢 ✓

这与 L4 提到的 online softmax(Milakov & Gimelshein 2018)是同一招;反向传播时论文再按 tile 重算(见 FA 论文 §3.1,"recompute tile-by-tile")✓

#### 补充 4:为什么"低精度 + 块缩放"会让 layout 变复杂

MX 格式里一个数 = 块 scale $s$(E8M0,每 32 个元素一个)× 元素 $q$(E4M3)。所以"元素"与"scale"的绑定关系依赖**存储顺序**:
- 转置/重排 ⇒ 32 元组的成员变了 ⇒ 必须重算 scale(或为转置单独存一份,即 P28 的 "transposes also separately quantized")✓
- tile 边界切断一个 32 元组 ⇒ 边界要特判 ✓
- 推论:量化与 tiling 必须**一起设计**(kernel 的量化/反量化点要落在 tile 边界上)✓

参考:OCP Microscaling (MX) 规范;讲义 P27–P29。
